# Decision log

Written before code (21 Nov 2026). Revisit only with a reason, and record the reason here.

| Topic | Decision | Why | Rejected |
|---|---|---|---|
| Platform | Standalone web application (not an Odoo module) | The brief asks for "one unified software platform" and mandates no platform. A web app lets crews use phones without Odoo licences. The domain model borrows Odoo's proven shapes (CRM lead → quotation → sales order → picking with serials → warranty → helpdesk → invoice) so Odoo judges recognise it. | Odoo addon: needs Docker/Odoo locally, and the PWA/3D/customer-portal ambitions fight the framework. |
| Product name | **Arka** (Sanskrit for the sun): "From the first enquiry to the twentieth year." | Echoes the brief's own promise ("first quote request to the 20-year warranty"). | — |
| Language | TypeScript end to end (Node 24 locally, Node 22 LTS in Docker) | One language for shared validation rules (client and server use the *same* zod schemas). The team already knows it from Round 1 and can explain it. | Python/Django (no shared validation with the browser). |
| API | Express 5 + zod + plain SQL (`pg`) | Boring and well understood. Async errors handled natively. Plain SQL lets us use the database features the brief needs: exclusion constraints, row locks, row-level security. | ORM (hides locking and RLS). |
| Database | PostgreSQL ≥ 15 (18.7 locally via `embedded-postgres`, no admin rights needed) | Money, stock and serial numbers need constraints and transactions. Extensions `btree_gist` (no technician double-booking, enforced by the DB) and `pg_trgm` (find a serial or phone from a fragment in milliseconds). | SQLite (no RLS, weak concurrency); BaaS (rules hide logic from judges). |
| Tenancy | Workspace per sign-up, isolated by PostgreSQL row-level security + composite foreign keys + startup self-test | Real SaaS for many installers; makes private one-click demo workspaces possible. Proven in Round 1. | Single-tenant (shared demo data gets trampled by judges). |
| Sessions | Opaque random session token in an httpOnly cookie; only its SHA-256 stored server-side | Instant revocation ("sign out everywhere", role change) without JWT expiry tricks. Fixes a Round-1 weakness. | JWT (can't revoke). |
| Passwords | Node's built-in `scrypt` | Memory-hard, no native dependency. | bcryptjs (slower pure JS, weaker). |
| Live updates | Server-sent events fed by Postgres `LISTEN/NOTIFY` | Works across several server instances. Round 1's in-memory hub only worked with one. | WebSockets (two-way not needed). |
| Files (site photos, signatures) | Stored in Postgres (`bytea`), compressed on the phone before upload (≤ 1600 px JPEG, ~250 KB), magic-byte checked on the server | Free hosts have ephemeral disks; photos are proof of work and must survive redeploys. A storage interface allows S3/R2 later. | Local disk (lost on redeploy); S3 (another account to set up). |
| Money and quantities | Money in integer **paise** (`bigint`); quantities `numeric(12,3)` compared in thousandths | No float drift in invoices or stock. | Floats. |
| Time | Company time zone (default `Asia/Kolkata`) defines today/week/month; weeks start Monday; financial year starts 1 April (invoice numbers `INV/26-27/0001`) | Brief asks for today/this week/this month; Indian invoicing uses the FY. | UTC boundaries (wrong "today" after 18:30 UTC). |
| Frontend | React 19 + Vite + React Router + TanStack Query + react-hook-form | Fast to build, code-splits well; Query + SSE gives "live" screens cheaply. | Next.js (SSR not needed; one more moving part on free hosting). |
| 3D | three.js via @react-three/fiber + drei, lazy-loaded; all assets self-hosted; static fallback | 3D that carries data: the landing story replays the brief's week, and the job/customer page draws the *actual* kit (panel count, inverter, battery). | CDN import maps (Round 1 lost icons when the CDN was blocked). |
| Barcode scanning | Native `BarcodeDetector` when available, ZXing fallback (lazy chunk), USB scanners as keyboard input | Works on Android Chrome, iPhone Safari and warehouse scanners. | Paid SDKs. |
| Email | Provider chain: Resend (HTTPS) → SMTP → log; codes redacted from logs; dev echo flag for tests | Render free blocks SMTP; never let one provider break sign-up. | Single provider. |
| Hosting | Render Blueprint (`render.yaml`): Docker web service + Postgres, `DATABASE_URL` wired by `fromDatabase`, secrets generated by the platform. Recommend a **non-expiring** database (Render paid or Neon free) for the judging window | Round 1's free DB expired and killed the demo. Blueprints avoid copying secrets by hand. | Hostinger shared hosting (no Node). |
| Tests | Vitest + Supertest against a real Postgres (embedded), Playwright e2e of the demo path, screenshot matrix | Real DB catches RLS, lock and constraint bugs that mocks hide. | Mocked DB. |
| Repo | Local git repo in `D:\odoo`; branch `main` only; nothing committed or pushed until the team says so; README carries an honest "How we built it" from the start | Round 1 had to rewrite history at the end. | — |

## Domain decisions

| Topic | Decision | Why |
|---|---|---|
| Lifecycle shape | Enquiry (lead) → qualification call → site survey (approve/reject) → quote (versioned; from kit template) → order/job → payments → pick list + installation visit → dispatch (serial scan) → delivered (warranty starts) → installation report (signature) → subsidy → closed. Service tickets hang off serials and customers. | Mirrors the brief's week scene by scene. |
| Quote gate | A quote can only be created for a customer whose latest survey is **approved** | Brief: "Only after the survey is approved should the customer receive a quote." |
| Kit templates | Template lines carry a quantity rule: `fixed`, `per_kw`, `per_panel`, `cable_run` (from survey cable distance) | "The exact list of parts should follow on its own." |
| Payment rule | Each job has a required advance (default 30 %, or full). The job is *confirmed* when payments reach it; confirmation creates the pick list and the installation visit automatically. | "Pays an advance, or the full amount, before work starts." |
| Serials | Panels, inverters, batteries and charge controllers are serial-tracked; everything else is quantity-tracked. Dispatch is refused until every serial line is scanned and each scanned serial is in stock, the right product, and unassigned. | "Each must be scanned before it leaves." |
| Warranty | On "delivered", each dispatched serial gets `warranty_start = delivery date` and `warranty_end = start + product.warranty_months` (inverter/battery/controller 24, panels 240 by default; editable per product). Replacements under warranty inherit the original end date. | "The warranty clock should start by itself." |
| Tickets | `open → assigned → in_progress → resolved → closed` (+ `reopened`). Coverage decided from the serial's warranty on the day the ticket opens. Closing needs customer confirmation (portal button or a logged confirmation). Out-of-warranty resolution creates an invoice from parts + labour automatically; covered repairs bill ₹0 and their cost is charged to the original job. | Scene 5. |
| Profit per job | Revenue (ex-GST) − parts issued at cost − technician hours × hourly cost − job expenses − warranty repair cost | Scene 6: "which installations made money, which lost money". |
| Subsidy | Default scheme PM Surya Ghar (residential, on-grid only): ₹30,000/kW for the first 2 kW, ₹18,000 for the 3rd kW, capped at ₹78,000. Editable per workspace. Paperwork tracked in stages. | Brief mentions the subsidy; scheme values change, so they're settings, not code. |
| Tax | GST rate per product (seeded: solar goods 5 %, installation service 18 %), editable | Rates change; keep them as data. |
| On-grid kit contents | The On-Grid kit template includes a charge controller, even though a grid-tie inverter usually has MPPT built in. | The brief defines the On-Grid kit as "inverter, wiring boxes, charge controller, panels, safety earthing and metal stands"; a reviewer flagged it, and we kept the brief's definition. The line can be removed from the template in Catalogue. |
| Warranty lengths | Inverters, batteries and charge controllers 24 months, panels 240 months by default. | These are the brief's own example (R17). Real products vary (inverters are often 5–10 years), so the length is a per-product field. |

## Security decisions (after an independent review)

| Topic | Decision | Why |
|---|---|---|
| Need to know | Purchase costs (`unit_cost_paise`, stock value) are returned only to the director, warehouse and accounts. Customer page links are returned only to the director, sales, support and accounts. Job money (payments, invoices, expenses) only to roles that read invoices or take payments. The server removes the fields; the screens handle their absence. | A technician needs the address and the kit, not margins or a link that opens the customer's private page. |
| Leaked links | `POST /api/customers/:id/new-link` replaces a customer's page token (audited); the old link stops working at once. | Customer pages are bearer links; a forwarded one must be revocable. |
| Email after commit | Quote, invoice and ticket emails are queued on the request and sent only after the transaction commits. | A rolled-back action must never have emailed the customer. |
| Public web form | It never overwrites an existing customer's saved details; differences are logged on the enquiry as "unverified changes" for staff to confirm. | Anyone can submit the form with someone else's phone number. |
| Abuse limits | Per-account sign-in limiter (on top of per-IP); at most 3 open complaints per customer page; 400 files or 300 MB per workspace per day; at most 300 live demo workspaces; 6 live-update streams per user; demo invites only to example.com addresses. | Bound what one person or one script can do to a shared deployment. |
